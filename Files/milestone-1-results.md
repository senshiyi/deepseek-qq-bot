# 第一里程碑实测报告

日期：2026-10-19，时区：Asia/Shanghai。测试仅在用户指定并同意的群与时段进行；具体群号、设备 ID 和用户反馈保存在忽略目录 `Results/local/`。不保存群原始音频。

## 结论与适用范围

固定音频通路的三项核心检查已在本机桌面 QQ 与另一台独立设备之间通过：程序收到对端讲话时的音频、对端确认听见程序测试音、安静且佩戴耳机时未观察到测试音直接回采。结果适用于本次单场通话和路由，不能代替长期运行、远端外放回音或多人抢话验收。

当前实现是固定音频联调工具。语音识别、DeepSeek 对话、合成服务、自动唤醒、有效插话判断和自动群图片入口尚未实现。

## 本轮环境与路由

- Windows 11，build 26200；.NET 10；NAudio.Wasapi 3.2.0。
- 本轮只有一个桌面 QQ 根进程，PID 为 19052。其命令行中的当前资源路径为 `versions/9.9.35-52892`；安装根目录启动器仍报告 9.9.25.42941，不将两者混称为同一个二进制版本。
- QQ 通话实际音频拥有者为子进程 24272（ppapi），不是仅凭 `audio.mojom` 名称猜测。
- 机器人播放 → **CABLE Input** → **CABLE Output** → QQ 通话麦克风。
- 群友讲话 → QQ 播放流 → 指定 QQ 根进程树采集。QQ 输出使用耳机，程序没有退回全系统采集。
- 23:16:19 的只读快照显示 QQ 的活动录音会话在 CABLE Output；物理 XIBERIA 麦克风的该会话为非活动状态。系统播放/录音的 Console、Multimedia、Communications 六项默认值均为 XIBERIA。

Windows“音量合成器”的 QQ **应用输入设备**从“默认”改为 CABLE Output。此前两个同路径 QQ 实例会共同受到这项偏好影响；本轮按用户选择仅保留一个桌面 QQ。恢复时只把 QQ 应用输入设回“默认”，随后重新核对实际录音流；已打开的流可能不会立即随偏好变化。不要使用“重置所有应用”，也不需要改系统默认麦克风。

## 自动化验证与延迟

既有无硬件回归 15/15 通过，加入单次WAV校验与取消后为21/21通过；另有有限探测入口的 7/7 针对复验，详见 [verification.md](verification.md)。它们覆盖取消、串行替换、过期队列数据、有界缓存及清理控制；模拟音频和服务不作为真实 QQ 成功证据。后续对话组件的测试与本里程碑分开记录。

| 指标 | 目标 | 本轮实测 |
| --- | --- | --- |
| 用户说完到机器人首次出声 | 后续接入识别/对话/合成后，短问答争取 2 秒以内，再按实测调整 | 尚无对话链路，未测；测试音播放时长不属于该指标 |
| 有效插话到机器人在远端停止发声 | 后续争取 300 ms 以内；须计入 QQ/远端缓存 | 自动插话未实现，未测；本地取消耗时不能替代 |
